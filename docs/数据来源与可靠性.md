# 数据来源与可靠性

> 原则：**数据必须真实可靠。能从确认可靠的事实固定推导出来的，可以合理推导；推导不出来的，坚决不臆造 —— 宁可显示"缺失/未标注"，也不给一个不可靠的值。**

这份文档逐项列出：每个字段**来自哪里**、属于哪一档可靠性、以及界面/JSON 里怎么体现。

---

## 一、三档证据等级

| 档 | 含义 | 处理方式 |
|---|---|---|
| **A 原始标注** | 数据集里直接写明的事实 | 原样使用，只做忠实翻译 |
| **B 可靠推导** | 由 A 档数据经确定规则算出，结果唯一、可复现 | 可以使用，但标明"推导" |
| **C 假设** | 数据里没有，靠先验猜的 | **必须显式标注**，且不能用于"结构性结论" |

C 档一旦混进 A 档，整条链路就不可信了 —— 所以下面每一行都标了档位。

---

## 二、CubiCasa5K → layout JSON 逐项对照

### A 档：原始标注

| 字段 | 来源 |
|---|---|
| 墙体几何 | `<g id="Wall">` / `Panel` / `Railing` 的 polygon |
| 门洞 | `<g id="Door">` 的 polygon |
| 窗/玻璃 | `<g id="Window">` / `Glass` 的 polygon |
| 房间多边形 | `<g class="Space Xxx">` 的 polygon |
| 房间类型 | 同一 class 的主类型 + 子类型（如 `Bath Shower`、`Closet WalkIn`） |
| 楼层划分 | `<g id="Floor-N">` 分组 |
| **房间真实尺寸** | `<g class="DimensionMeasureLabel">` 里的印刷尺寸文本（如 `13'6" x 20'4"`）→ **用于确定毫米尺度** |
| **固定家具位置与尺寸** | `<g class="FixedFurniture Xxx">` 的 polygon（坐标需按祖先链 transform 复合，与官方 `get_icon` 一致） |

房间名只做**翻译**，不归并：`TechnicalRoom → 设备间`、`Utility → 家政间`、`Undefined → 未定义空间`。翻不出来的标签**保持英文原样**（如 `Den`），不猜中文名。

> 官方 `room_name_map` 里 `Utility`、`TechnicalRoom`、`SunRoom` 都被压成 `Room` —— 那是为 12 类分割任务做的有损压缩，**不用于显示**，否则会丢掉数据里本有的信息。

### B 档：可靠推导（可用，但标明）

| 字段 | 推导规则 | 为什么可靠 |
|---|---|---|
| 外墙 / 内墙区分 | 墙体是否贴着外包络 | 完全由几何决定，结果唯一 |
| 分段尺寸链 | 沿每条边取墙体断点，相邻断点间距 | 是该模型内部几何的**精确测量**，不是原图纸的标注 |
| 房间面积（相对值） | 鞋带公式 | 纯几何 |
| 房间名称排序/面积排序 | — | 纯计算 |

### A 档补充：毫米尺度（2024 修订，已从"假设"升级为"实测"）

**结论：CubiCasa5K 的 SVG 用户单位 = 10 mm（1 单位 = 1 cm），这是数据集自带的固定比例。**

依据：SVG 里每个房间组（`g.Space Xxx`）内嵌着原图纸印刷的**房间真实尺寸**
（`DimensionMeasureLabel`，文本如 `13'6" x 20'4"`）。用「真实面积 ÷ 像素面积」即可逐房间反解比例：

| 房间（样本 13451） | 像素 bbox | 标注尺寸 | 反解 | 长宽比 |
|---|---|---|---|---|
| Kitchen | 240×365 | 2388×3658 mm | 9.98 | ✓ |
| LivingRoom | 501×491 | 5004×4902 mm | 9.99 | ✓ |
| Bedroom | 381×351 | 3810×3505 mm | 9.99 | ✓ |
| Bath Shower | 217×179 | 2159×1778 mm | 9.95 | ✓ |

规模验证：**313 套 / 706+ 个标注**，每套反解值 `min 9.65 / p1 9.95 / 中位 10.00 / p99 10.02 / max 10.03`，
**偏离 10±0.5 的套数：0**；同一套内多个房间的互差中位仅 1.03×。

残留误差：标注按**英寸取整**（`5'4"` 实际可能是 1620–1640mm），因此约 **±1~2%**。

两种取法（转换器自动选择）：

| 情况 | 做法 | JSON |
|---|---|---|
| 本套 SVG 有尺寸标注（几乎全部） | 用本套实测值 | `scale.basis: "dimension-labels"`、`labelsUsed: n` |
| 本套没有标注 | 用数据集常数 10 mm/单位 | `scale.basis: "dataset-constant"` |

**已废弃的做法**：早期用「单开门 800mm」先验反推。实测证明它系统性**偏高约 10%** ——
真实门宽约 **720mm**，不是 800mm（把先验与标注口径相比，比值中位 0.91）。
该先验现在只作为诊断量保留在工具里，不参与出图。

### C 档：假设（目前为空）

CubiCasa5K 这条链路上**已经没有纯假设字段**了 —— 尺度已由数据自带标注确定。
R2V 数据集仍然如此（它的文件里没有任何尺寸文字，尺度只能靠先验）。

### D 档：数据里没有 → 保持缺失，不推断

| 字段 | 情况 | 现在的做法 |
|---|---|---|
| **承重墙** | CubiCasa 只有一种 `Wall`，**没有任何承重标注** | 数据里一律不猜：内部墙标为普通墙，JSON 里 `bearingAnnotated: false`，界面提示「无承重墙标注」<br>**但应用内可以人工补**：用「承重墙」工具（快捷键 `B`）点墙体切换承重/非承重，标记存进 `state.bearing`，随方案 JSON 保存、可撤销 |
| **活动家具**（床 / 沙发 / 餐桌 / 椅） | CubiCasa 的 `FixedFurniture` 只标**固定家具**（54 类：橱柜、洁具、家电、桑拿凳、壁炉…），**不标活动家具** | 不生成、不猜。卧室/客厅保持空置，需手动摆放 |
| 房间用途细节（是否主卧、朝向） | 数据没有 | 不推断 |

> **固定家具已转换**：`wardrobe / counter / cabinet / ksink / shower / toilet / fridge / washer / dishwasher / dryer / bathtub`
> 共 11 类，171/172 套有家具、平均 33.3 件，位置与尺寸都来自原始标注。
> 未映射的类别（桑拿凳、壁炉、烟囱、电器预留位、衣帽架、Misc）**跳过并在报告里列出**，不硬凑成某个家具。

> 曾经做错并已撤销：早期把"贴外包络的墙"标为承重墙（红色、禁止拆除）。这是把假设当结论 —— **外墙≠承重墙**（内部剪力墙也是承重墙），现在已改回 `e`（外墙）。

## 三、其它数据源的情况

| 数据源 | 房间 | 墙 | 窗 | 尺度 | 承重墙 |
|---|---|---|---|---|---|
| **CubiCasa5K** | A（多边形） | A（多边形） | A | **C（假设）** | **D（缺失）** |
| **R2V / ICCV 2017** | A（种子点）→ B（连通域恢复） | A（中心线）→ B（按 200mm 膨胀） | **D（缺失）** | **C（假设）** | **D（缺失）** |
| 手写示例 `layout-4br-2lr-2ba.json` | 人工设计 | 人工设计 | 人工设计 | 人工给定（mm） | 人工标注 |

R2V 那条链路里，墙厚 200mm 同样是**假设**（数据只给中心线，没给厚度）。

## 四、界面上怎么体现

载入的户型若带缺失项，**顶部副标题会直接标出来**：

```
套内使用面积约 117.69 m² · 15 间房 · 尺寸单位 mm · ⚠ 无承重墙标注
```

（尺度已经实测确定，不再提示"估算"；只有承重墙这一项仍然是缺失。）

内置的三室两厅两卫是人工给定毫米尺寸、明确标注承重墙的，所以没有这个警告。

## 六、尺度是怎么从"假设"变成"实测的"（已完成）

原本打算外购一个带真实尺寸的数据源（ZInD / Structured3D / RPLAN 之类），但那些都要手动下大文件。
后来发现**真实尺寸本来就在 CubiCasa5K 的 SVG 里**：

1. 每个房间组内嵌 `DimensionMeasureLabel`，文本是原图纸印的房间尺寸（英尺英寸，按英寸取整）；
2. 标签是房间组的**子元素**，所以不需要坐标匹配 —— 在谁的组里就是谁的尺寸；
3. `mm/单位 = sqrt(真实面积 ÷ 像素面积)`，并用长宽比做一次校验；
4. 313 套 / 706+ 个标注实测：**10 mm/单位**，偏离超过 ±0.5 的样本为 **0**。

复查命令：

```powershell
# 逐房间打印「像素 bbox vs 标注尺寸 vs 反解比例」
node tools/dimlabel-detail.mjs <某套>/model.svg

# 批量统计（含离群检查）
node tools/dimlabel-detail.mjs --scan .cache/cubicasa5k 300
# 或
node tools/dimlabel-scale.mjs .cache/cubicasa5k 300
```

**仍然只能靠先验的**：R2V 数据集（它的文件里没有任何尺寸文字）。对它的输出，`estimated` 仍为 `true`。

## 六之二、承重墙：从"缺失"到"人工可信"（应用内标注）

三个公开数据集都没有承重墙标注，所以**数据层面永远是缺失**。但"这面墙能不能拆"是看图的人一眼能判断的事，
所以应用里提供了标注入口：

1. 选工具箱里的「**承重墙**」（快捷键 `B`）——会自动打开「承重墙」图层，否则标了看不见；
2. 点一下墙体 → 变红（承重、禁止拆除），再点一下 → 取消；
3. 标记存在 `state.bearing`（`'w'+墙下标`），与 `demolished` 同级，因此：**进撤销栈、进方案 JSON、进 localStorage**；
4. 顶栏副标题会从 `⚠ 无承重墙标注` 变成 `已人工标记 N 道承重墙`；方案统计里也多了一行「承重墙 N 道（人工 M）」。

边界说明（诚实版）：

| 情况 | 行为 |
|---|---|
| 数据自带 `t:'b'` 的墙（内置三室户型） | 已承重，不需再标；点了会提示"已由原数据标注" |
| 外墙（`e`） | **不参与**承重标记 —— 外墙 ≠ 承重墙，两者语义不同，不混为一谈 |
| 矮墙（`low`） | 不参与 |
| 载入新户型 | `state.bearing` 清空（属于上一个户型），需重新标 |

**这是唯一能把承重墙从 D 档提升到 A 档的路径 —— 靠人的判断，而不是我的推断。**
标注的可信度取决于看图的人；工具不替你做决定。

## 七、自查清单

拿到任何一个 layout JSON，按这个顺序问：

1. `estimated` 是 `true` 吗？→ 尺度是推定的，面积只能当估算（R2V 转换结果会是 true；CubiCasa5K 的是 false）。
2. `scale.basis` 是什么？→ `dimension-labels`（逐套实测）/ `dataset-constant`（数据集常数）/ `door-width-prior`（已废弃的先验）。
3. `bearingAnnotated` 是 `false` 吗？→ 没有承重墙信息，拆墙前必须核对结构图。
4. `wins` 为空数组吗？→ 该数据源没有窗标注（R2V 就是这样）。
5. `furniture.items` 里只有橱柜/洁具/家电这类吗？→ 说明只有固定家具；床、沙发、餐桌**不会**出现，属数据缺失，不是转换漏了。
6. `dimChainsSource` 是 `derived-from-wall-breakpoints` 吗？→ 尺寸线是算出来的，不是原图标注。
